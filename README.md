# Omnia — self-hosted AI workspace

A Claude-style AI workspace you run yourself. Chat with **5 providers**, delegate agentic work to **N concurrent Docker sandboxes** with a live browser, generate and view **PDF / DOCX / XLSX / Markdown / code** artifacts, and wire in **MCP tools, skills, and web search** — all with thinking animations, streaming search results, and a Manus-style mini-computer above the chat box.

Built on the fastest modern stack: **Next.js 16 (App Router, Turbopack) · React 19 · TypeScript · Tailwind v4 · AI SDK v7 · Playwright/Chromium in Docker**.

---

## Features

- **6 chat providers** — OpenCode Zen, Anthropic Claude, OpenAI, Google Gemini, Ollama, LM Studio (OpenAI-compatible). Pick any model in the header dropdown; the key indicator shows which providers are configured.
- **Web search like Claude** — DuckDuckGo search with a Claude-style "Searching the web…" card, source chips, and ranked result cards (with rate-limiting + HTML fallback).
- **Thinking animations** — animated reasoning blocks for Anthropic extended thinking / Gemini thinking / OpenAI reasoning models.
- **Artifacts + viewers** — the model can `createArtifact` anything (code, HTML, SVG, Mermaid, table, Markdown) and you open it in the side panel with proper viewers: PDF (pdfjs), DOCX (docx-preview), XLSX (SheetJS), CSV, Markdown, code, images, and sandboxed HTML.
- **Agentic chat** — the chat loop runs with `webSearch`, `createArtifact`, and `runAgentTask` tools (turn them on/off with the toggles above the composer).
- **Replies survive the tab** — every answer is generated by a **server-side chat run**, not by your browser tab. Close the window, switch conversation, or open the app in another tab: the run keeps going, checkpoints the transcript to disk, and any client that shows up attaches over SSE to watch it live (with a banner + sidebar indicator telling you *what it's doing right now*).
- **N concurrent agents in Docker** — spawn any number of agents from the **Agents** panel or by asking the chat. Each one runs in its own isolated Docker container with a shell, filesystem, Chromium browser, and file-generation libraries (PDF/XLSX/DOCX/CSV). Streams live progress + logs; result files are harvested into the Artifacts panel. Engines: **AI SDK tool-loop** or the **Claude Agent SDK**.
- **Mini-computer view** — live screenshots of each agent's browser/screen stream above the chat box (Manus style). Click one to open the full Sandbox panel: live screen, terminal, and output files.
- **Skills** — custom instructions the model follows in conversation (like Claude's Skills).
- **Connections (MCP)** — add stdio or HTTP MCP servers and connect their tools to the chat.

## Quick start

Requires **Node.js 20+** and **Docker**.

```bash
# 1. install the app
npm install

# 2. copy env & add at least one API key
cp .env.example .env

# 3. build the sandbox image (Chromium + Playwright + file libs — a few minutes first time)
npm run sandbox:build

# 4. start the sandbox service (spawns agent containers)
npm run sandbox          # listens on 0.0.0.0:8787

# 5. run the app
npm run dev              # http://localhost:3000
```

> **Why the sandbox service runs on the host (not in Compose):** it provisions agent containers via the Docker daemon and passes absolute host paths as volume mounts. Those resolve correctly only when the service runs on the host where Docker lives. `node sandbox/server.mjs` is the supported way.

Then ask the chat to do agentic work:

> "Use an agent to research web framework usage in 2026 and produce a PDF report in /workspace/out"

or spawn agents directly in the **Agents** panel (⚡ button in the header).

## How the sandbox / agents work

```
Next.js app ──proxy──> sandbox service (:8787) ──docker──> N × omnia-sandbox containers
                              ▲   ◀── events / screenshots (host.docker.internal)
                              │
                       runner.mjs inside each container:
                         AI SDK tool-loop  OR  Claude Agent SDK
                         tools: web_search, browser_*, exec_command,
                                create_file, create_pdf/xlsx/docx/csv
```

- Each agent gets its own container (`--memory 4g --cpus 2`), its `/workspace` mapped to `data/sandboxes/<id>/workspace` on the host, and its own **Chromium** browser.
- The runner streams **events back to the sandbox service** over `http://host.docker.internal:8787/agent-events/<id>` (screenshots are small JPEGs) → the service relays them via SSE → the app updates the mini-computer + Agents panel live.
- Files saved under `/workspace/out` become downloadable from the Sandbox panel and are harvested into the **Artifacts** panel when the agent finishes.
- Kill a sandbox any time from its mini-computer window or the Sandbox panel.

`node sandbox/server.mjs` endpoints: `GET /health`, `POST /containers`, `GET/POST /containers/:id/...` (`exec`, `write`, `read`, `list`, `download`, `screenshot`, `kill`, `start`), `GET /containers/:id/events` (SSE), `POST /agent-events/:id` (runner ingestion).

## How chat replies work (background runs)

```
browser ──POST /api/chat──> chat run (lib/chat-runs.ts) ──> provider stream
   ▲                             │  owns the generation, not the response
   │                             ├─ checkpoint → data/conversations.json (throttled + on finish)
   └──GET /api/chat/runs/:id/events (SSE: replay from chunk 0 + live tail)── attach/detach
```

- `POST /api/chat` starts a run and streams it (the response carries `x-chat-run-id`); `POST /api/chat/runs` starts one and returns `202 { runId }` without streaming. Either way the run lives on the server, so **closing the tab no longer cancels the reply**.
- A run consumes its own model stream (no `tee()`), records every `UIMessageChunk`, tracks a human-readable activity ("Thinking…", "Searching the web…", "Running a sandbox agent…"), and serializes transcript writes so a slow checkpoint can't overwrite the final one.
- Clients attach with `GET /api/chat/runs/:id/events` (SSE, same framing the AI SDK parses) after loading `GET /api/chat/runs/:id` — the snapshot is the transcript plus the **partial assistant message with the same id as the replay**, so `useChat.resumeStream()` replaces that bubble instead of duplicating it.
- `GET /api/chat/runs?conversationId=…` lists runs (status, activity, step, elapsed) for the sidebar indicator and for a tab that joins late; `DELETE /api/chat/runs/:id` stops a run and keeps the partial answer.
- Runs are created with the model already built, so an unconfigured provider still answers with a normal error instead of failing invisibly in the background. One run per conversation (a second attempt gets `409`); the composer blocks sending until you stop the live one.
- Provider errors that happen mid-stream travel through the run as `error` chunks, so both attached and returning clients see the same message the old streaming route produced.

## Notes

- **XLSX** generation/reading uses SheetJS `xlsx@0.18.5` client-side; two known advisories (GHSA-4r6h-8v6p-xvw6, GHSA-5pgg-2g8v-p4x9) apply to parsing *untrusted* spreadsheets with arbitrary code execution enabled. Here it runs read-only in the viewer; accepted for local self-hosted use.
- **Chat runs live in memory.** A finished run stays queryable for ~10 minutes so a returning client can still see it, but restarting the server drops in-flight runs — the last checkpoint (≤4 s old) is what you're left with. The transcript, not the run, is the durable record.
- **One run per conversation.** Sending while a background reply is generating is blocked (the server would return `409`). Press Stop first — that aborts the provider stream and keeps the partial answer.
- **No data leaves your machine** except provider API calls and (optionally) web search. Conversations, artifacts, skills and MCP config are stored as JSON under `data/`.
- The **Claude Agent SDK** is installed best-effort inside the sandbox image (it's ~300 MB). If its install fails, `agent-sdk` engine agents automatically fall back to the AI SDK tool-loop engine.
- The sandbox service binds `0.0.0.0:8787` so containers can reach it via `host.docker.internal` — don't expose it to untrusted networks.
